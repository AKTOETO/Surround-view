# Требования к системе Surround View

## Назначение и статус

Рабочая редакция от 04.10.2026; основа от 19.09.2026 по [аудиту](../archive/AUDIT.md). Это спецификация планируемой системы; наличие документа не подтверждает реализацию или достижение метрик. Требование выполнено, когда существует реализованное поведение и подходящее свидетельство: тест, инспекция или измерительный протокол.

Тема, цель и задачи определены в [[research/TOPIC]]. Эти требования уточняют рабочую постановку по ОС Аврора. Bowl, GPU и интерактивный ракурс сами по себе не являются доказательством новизны.

## Область и приоритеты

**MUST** — обязательный защищаемый результат. **SHOULD** — желательное расширение; отсутствие объясняется в отчёте. **COULD** — дополнительная возможность после завершения основного исследования. Приоритет требования о метрике означает обязательность измерения; численный порог остаётся предварительным до фиксации профиля по [ACCEPTANCE.md](../validation/ACCEPTANCE.md).

| Уровень | Состав |
|---|---|
| Исследовательское ядро | `sv-core`: модель `opencv_fisheye`, плоскость и аналитическая bowl, равномерная сетка, независимый CPU-эталон, GPU-проекция, маски, blending, виртуальная камера; `sv-bench` для опытов |
| Минимальный демонстрационный стенд | Один Linux-узел; отдельный `sv-server`; `sv-client` на Qt версии из паспорта платформы, Qt Quick (QML) [[references/DEVELOPMENT#S45\|S45]]; лёгкий `sv-simulator` как producer; локальный replay без simulator; trace |
| Целевой результат | `sv-configurator`, первоначальная/повторная калибровка и диагностика смещения; `sv-client` и GPU-конвейер на реальном устройстве с ОС Аврора |
| Желательные интеграции | Реальная калиброванная запись, live-адаптер, передача GPU-буфера при измеренном узком месте; CAN/сенсоры только для конкретного сценария |
| Дополнительные возможности | Полный интерактивный 3D-мир, динамика автомобиля, pan, hot-swap, горячая калибровка, другой графический API, сетка с учётом ошибки проекции |

Обязательных физических камер ровно четыре: `front`, `right`, `rear`, `left`. Отсутствие одной — отказ, а не отдельная конфигурация системы с меньшим числом камер. Габариты, калибровка и поверхность меняются данными. Два физических компьютера и конкретное головное устройство не являются условиями минимального стенда.

## Термины и исследовательские задачи

Проекционная поверхность — условная 3D-геометрия для отображения изображений, а не восстановленная сцена. Физическая камера формирует вход; виртуальная камера задаёт выходной ракурс. Набор кадров содержит выбранные входы с их идентификаторами и временем. Возраст набора вычисляется по старейшему входу; skew — разброс времён входов в общей шкале. Программная сквозная задержка заканчивается событием передачи результата на представление в UI и не равна измерению появления пикселя на экране.

Задачи R1–R6 и их результаты: [[research/TOPIC#Задачи]]. Здесь используются те же ID.

## Границы результата

Обязательны orbit, zoom и пресеты; допустимая область задана в конфигурации. Скрытые стороны препятствий не восстанавливаются, вертикальные объекты могут растягиваться и двоиться. Покрытие и фотометрические швы оцениваются отдельно. Полноценная реконструкция, SLAM, оценка глубины, собственные нейросети, аппаратная синхронизация и функциональная сертификация не входят в объём.

Чтение фиксированного набора MUST; live-recorder SHOULD. Независимый CPU-эталон MUST. Смена адаптера между запусками MUST, hot-swap COULD. Критерии приёмки метрик задаёт NFR; конфигурация и паспорт фиксируют применённые значения. Предлагаемые аудитом ID `RES-*` распределены по действующим требованиям, отдельный дублирующий набор не вводится.
