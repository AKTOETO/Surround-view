# Последовательный запуск исследований в C++

`svctl research-batch` запускает несколько сценариев через общий `sv-research` и
`sv-client-lib`. Сервер исполняет алгоритмы; клиентский application service фиксирует план,
собирает результаты и оценивает внешний эталон. Python dispatcher не используется.
Это первый срез supervisor: один уже запущенный сервер и одна подключённая replay-запись.
Он не запускает серверные процессы, не меняет recording, не создаёт Blender-изображения.

## Запуск и формат плана

Сервер должен работать с replay manifest, содержащим достаточно кадров для каждого сценария.
Пример после обычного запуска сервера из [[engineering/USAGE]]:

```sh
build/svctl --unix /tmp/sv-prototype --timeout-ms 5000 \
  research-batch configs/research/batch-repeatability.json artifacts/batch-repeatability-01
```

Для удалённого сервера замените `--unix DIR` на `--tcp HOST CONTROL_PORT DATA_PORT`.
Родитель output должен существовать, а сам каталог — отсутствовать. Каждый новый запуск
использует новое имя. Нельзя выбирать существующий пустой каталог или symlink.

```json
{
  "schema_version": 1,
  "runs": [
    {"id": "sequence-a", "scenario": "multiband-matrix.json"},
    {"id": "sequence-b", "scenario": "multiband-matrix.json"}
  ]
}
```

Относительный `scenario` разрешается от каталога batch plan. Относительный `quality_reference`
внутри сценария — от каталога самого сценария. Output paths не задаются участниками:
они выводятся из безопасного ID. Допустимы ASCII буквы/цифры/`_`/`-`, длина 1–64;
ID уникальны, `batch` зарезервирован для summary. Неизвестные поля отвергаются.

Пределы: plan 64 KiB, 1–8 участников, scenario до 1 MiB, суммарно до 10000 trials
с warmup и до 128 MiB удерживаемых RGB/mask pixels. Во время загрузки очередного эталона
до проверки суммарного бюджета возможно временное превышение последнего предела;
это не предел общей RSS. Все сценарии обязаны явно задавать `reset_replay: true`.
Формат сценария/порядок trials — [[architecture/RESEARCH_RUNTIME]], эталонов —
[[engineering/RESEARCH_QUALITY]]. Пример выше повторяет одну матрицу для проверки
воспроизводимости; второй запуск не является независимой scene или holdout.

## Предварительная проверка и исполнение

До любого подключения загружаются и проверяются **все** сценарии и эталоны, включая hashes
пикселей и guards. Они удерживаются неизменяемыми в памяти. Затем создаётся новый output,
эксклюзивно резервируются summary, все отчёты и capture directories. Ошибка позднего
участника или output preparation не должна запускать ранних участников.

После подготовки участники исполняются в порядке плана. Каждый получает отдельную
клиентскую сессию и lease, выполняет reset, свою матрицу и restore fusion/surface/pause.
Следующий начинается только после завершения предыдущего. Семантика restore ограничена:
старый replay cursor, OS/GPU caches и серверный процесс не восстанавливаются.

Lease не удерживается между участниками; другие клиенты могут менять состояние в этом
интервале. Серия не является глобальной атомарной транзакцией, и endpoint сам по себе не
доказывает неизменность процесса/записи. Фактические input/model/view identities и состояния
нужно проверять по каждому отчёту; общая process/dataset registry остаётся отдельной задачей.

Если workflow или restore провалился, либо evaluator обнаружил несовпадение guards,
оставшиеся участники не запускаются. Если workflow успешен, но заранее заданный quality
threshold не пройден, остальные участники продолжают исполняться: это научный результат,
а не технический отказ. Флаг отмены API проверяется между участниками и внутри общего runner.
Отмена активного прогона проходит его обычный путь restore. CLI пока не предоставляет
обработчик Ctrl+C через этот флаг; завершение процесса не заменяет штатную отмену.

## Результаты и коды завершения

В новом каталоге находятся `batch.json`, `ID.json` и при capture — `ID.json.frames/*.rgba`.
Ссылки `rgba_file` разрешаются от каталога **индивидуального** отчёта.
У каждого отчёта есть `scenario_input_sha256`: hash исходных байтов сценария при загрузке.
Он отличается от существующего `scenario_sha256`, который описывает нормализованную
исполняемую конфигурацию. Summary содержит raw plan hash, семантический plan snapshot,
сценарные hashes, результаты каждого участника и ссылки на отчёты.

| Поле summary | Значение |
|---|---|
| `scope` | `same_server_recording_v1`: текущий ограниченный workflow |
| `status` | `complete`, `failed` или `cancelled` |
| `completed` | Успешно завершённые workflow с подтверждённым restore, включая quality rejection |
| `reported` | Участники, вернувшие и записавшие отчёт, включая технически неуспешные |
| `runs[].status` | `not_started`, `reported` либо `error` при исключении без возвращённого отчёта |
| `success` | Все workflow выполнены; само по себе не означает принятое качество |
| `restored` | Подтверждённый restore; при отмене до первого подключения — true, изменений не было |

Policy `all_defined_member_criteria_v1` учитывает заданные критерии участников:
`failed`, если хотя бы один завершённый участник не прошёл пороги; `passed`, если все
заданные критерии пройдены; `not_requested`, если критерии нигде не заданы. Участники без
критериев не становятся научно принятыми из-за aggregate `passed`. Неполная/неуспешная серия
всегда даёт `incomplete`. Counts `reported_criteria_members`/`failed_criteria_members`
относятся к уже записанным отчётам, не к ещё не запущенным участникам.

CLI выводит JSON со ссылкой на `batch.json`; exit 0 — успешный workflow с passed/not_requested,
5 — полностью исполненная серия с quality rejection, 4 — failed/incomplete/cancelled,
3 — исключение подготовки/IO. Аргументы неправильной формы дают 2.

Отчёты резервируются заранее и не перезаписываются. Не запущенные участники оставляют
пустые резервные файлы. Ошибка подготовки может оставить частичный каталог; используйте
новый output, не принимайте существование файла за завершённый опыт. Summary записывается
только в конце; durable checkpoints, crash recovery и resume ещё не реализованы.

## API и проверки

`FileExperiment` использует PImpl и отделяет загрузку immutable inputs от резервирования output
и одноразового исполнения. `run_batch(plan, directory, options, cancel, progress)` предоставляет
общий blocking service; progress передаёт `(member_index, completed_trials, total_trials)`.
GUI вызывает service вне UI thread: callback обновляет atomic counters, UI читает их таймером,
terminal result доставляется через queued callback. Запуск сохранённого batch реализован ниже;
редактор состава batch из готовых сценариев также реализован ниже. Это application service над `sv-client-lib`, а не новая
серверная команда.

Проверки: `research_batch_tests.cpp` — предварительная проверка, bounds, отмена до сети,
immutable сценарий, single-attempt и защита output aliases; `test_client_transport.py` —
настоящие Unix/TCP сессии, воспроизводимость RGBA между участниками, quality rejection с
продолжением и source-content mismatch с остановкой/restore. Сводка — [[validation/RESEARCH_RUNTIME]].

## Исследование из sv-simulator

Запустите replay server обычной командой из [[engineering/USAGE]], затем клиент:

```sh
build/examples/sv-simulator/sv-simulator --unix /tmp/sv-prototype
# Для удалённого сервера:
build/examples/sv-simulator/sv-simulator --tcp HOST CONTROL_PORT DATA_PORT
```

1. Дождитесь подключения и завершения локальных configuration requests. Откройте **Исследования**
   в шапке окна. Для формы настройте поверхность и виртуальный ракурс заранее на основной странице.
2. В **Источник плана** выберите форму либо сохранённый сценарий. Форма позволяет выбрать методы,
   frames/warmup/repeats/seed, boundary/levels и seam solver. Обе boundaries размножаются только
   для multiband методов, solver применяется только к graph-cut. Список методов пока фиксирован;
   несовместимые с сервером настройки приводят к отказу, а не к автоматической подмене метода.
3. Для формы можно нажать **Выбрать…** в группе **Внешний эталон**. Выбирается существующий
   reference manifest, совместимый с frames, source/model/view guards и размером output.
   **Убрать** отключает оценивание. Предпочтителен schema2 с pixel/model identities.
   Пороговые criteria читаются из manifest до запуска; эта форма их не редактирует.
4. В режиме сохранённого сценария выберите scenario JSON через файловый диалог. Файл не
   изменяется. Его reference разрешается от каталога исходного файла (после canonical resolution),
   значения формы/её reference не применяются. Все поддерживаемые runner поля сохраняются,
   включая surface, matrix, reset_replay и capture_frames. Для серии выберите отдельный режим «Запустить batch-план».
5. Укажите новый output с существующим родителем. **Новое имя** предлагает путь
   `artifacts/gui-research-UTC-COUNTER` относительно cwd приложения. Frames должны помещаться
   в подключённую запись; автоматического определения её длины пока нет. В форме default frames=2.
6. Нажмите **Начать исследование**. Worker проверит и зафиксирует сценарий и reference **до
   создания output и подключения**. Затем резервирует отчёт/captures и вызывает тот же C++
   FileExperiment, что CLI. При импорте бюджет trials появляется после preflight. 100% trials
   ещё не означает завершённый restore.
7. **Отменить и восстановить настройки** запрашивает штатную отмену. Текущая синхронная операция
   завершается, затем runner исполняет restore. Закрытие окна также запрашивает cancel и ждёт
   terminal callback; окно может закрыться и при сообщении о неудачном восстановлении.

### Результаты и смысл статусов

**Результаты** показывают terminal status, reference kind/dataset/schema, критерии отдельно от
workflow, timing rows и masked RGB8 MAE/RMSE/PSNR. Прочерк означает отсутствие данных.
Малая ненулевая ошибка выводится значащими цифрами, а не округляется в `0.000`.
Точный RGB match имеет PSNR `null` + `exact_match=true` в JSON и `∞ (точное совпадение)` в UI.

| Состояние | Что означает |
|---|---|
| passed | Все заданные критерии пройдены при завершённом workflow/restore |
| failed | Workflow/restore завершены, минимум один threshold не пройден; код 5 |
| not_requested с reference | Критерии не заданы; при успешном workflow метрики рассчитаны |
| not_requested без reference | Качество не оценивалось |
| incomplete | Заданные критерии не могут быть оценены полностью, например guard mismatch или cancel |
| not_available | Подготовка не выполнена, отчёт текущего запуска отсутствует |

Если criteria отсутствуют, acceptance остаётся not_requested даже при техническом отказе;
проверяйте workflow/restore и terminal code отдельно. Критерии проверяются на всех measured
samples, не на округлённой таблице. `regression` явно
показывается как проверка воспроизводимости; `independent_ground_truth` — заявление автора,
программа не доказывает независимость/истинность reference и обоснованность порогов.
Новая неуспешная подготовка очищает прежний badge/rows/report path, чтобы старое passed не
выглядело результатом нового запроса. Сохранённые файлы прежнего запуска при этом не удаляются.

Quality summaries используют один результат на frame_index без warmup/repeated counting.
MAE взвешена выбранными pixels, RMSE вычислена из общей MSE, PSNR — из этой MSE, не из среднего
PSNR отдельных кадров. `frames` в quality row — число уникальных оценённых кадров; `n` timings
включает measured repeats. Render-wall p50/p95 описывают paused samples, не sustained FPS.
Viewer остаётся дополнительным потребителем; GUI timing не равен headless qualification.

### Файлы и происхождение входов

Из формы сохраняется `scenario.json` с абсолютным reference locator, `report.json` и measured
`report.json.frames`. Snapshot воспроизводится через обычный `svctl research` при сохранении
исходных reference/RGB/mask файлов. Dataset не копируется и не становится переносимым bundle.
При импорте source scenario не копируется и не перезаписывается: сохраняются report и captures,
если их запросил исходный сценарий. Сохраняйте исходный scenario и его reference hierarchy.

`scenario_input_sha256` всегда хэширует точные переданные JSON bytes. Дополнительные поля:
`scenario_input_kind=file_bytes_v1` либо `memory_json_bytes_v1`, `scenario_input_base_directory`
и `scenario_input_path` для исходного файла. Для формы hash совпадает с bytes сохранённого
snapshot, включая newline; для импорта — с исходным файлом. Semantic `scenario_sha256` имеет
прежний смысл. FileExperiment принимает либо path, либо bytes + явную reference base; в обоих
случаях данные загружаются неизменяемыми до сети. Уже загруженный reference passport сохраняется
и при отмене до начала оценки, без утверждения о наличии измерений.

### Worker и проверки

Endpoint/form замораживаются перед запуском. Потеря viewer availability не перенаправляет
текущий worker на другую машину. UI poll atomic counters раз в 100 мс; terminal callback
передаёт строки вариантов, не полный report. Основные настройки/orbit блокируются на время
работы, после возврата запрашиваются active/revision. Это не изоляция от других клиентов.
Destructor выполняет cancel/join; общая длительность shutdown зависит от текущего OS/driver IO.

Проверки: native unit types/bounds/preflight/малые ошибки; live Unix/TCP/combined для импорта и
формы при passed/failed/not_requested/incomplete; настоящий QML запуск сохранённого сценария
с reference и отображением его результатов. Файловый диалог открывается/отклоняется в QML tests,
выбор не запускает исследование сам. ResearchCloseGuard откладывает close до terminal callback;
window case использует отказ подготовки без сети, настоящий restore проверяется live cases.
Трасса взаимодействий: рисунки RR.7–RR.8 в [[architecture/RESEARCH_RUNTIME]].

Остаются carrier/general matrices, capabilities-driven choices, редактирование
criteria с фиксированием до запуска, bundle import/export, сравнение разных reports и durable
resume. Текущий импорт одиночного scenario не закрывает multi-recording registry/switching.

### Запуск batch-плана из GUI

1. Подключитесь к replay-серверу с нужной записью. Откройте **Исследования → План**.
2. В «Источник плана» выберите **Запустить batch-план**, затем файл, например
   `configs/research/batch-repeatability.json`. Этот пример требует не менее трёх frame sets.
3. Задайте новый каталог с существующим родителем и нажмите **Начать исследование**.
   Настройки формы и её reference к batch не применяются: каждый участник берёт собственный
   сценарий и reference. Все участники проверяются до создания outputs и подключения.
4. На вкладке **Выполнение** наблюдайте номер участника и trials **текущего** сценария.
   Счётчик сбрасывается перед следующим участником. Он не является общим процентом серии.
   Отмена ждёт текущую операцию/restore и не запускает следующие сценарии.
5. На вкладке **Результаты** проверьте общую сводку и каждую карточку: техническое завершение,
   критерии качества, подтверждение restore, статус `not_started`/`error`/`reported` и имя отчёта.
   Полный путь указывает на `batch.json`; `ID.json` и captures лежат рядом согласно CLI-контракту.
   Сводка GUI не загружает member reports повторно и не показывает их timing/quality tables.

Провал критериев (`failed`, код5) продолжает серию; guard/technical failure (`incomplete`, код4)
или отмена останавливают её. `reported` означает сохранение отчёта, а не успешную научную приёмку.
У `not_started` нет подтверждённых workflow/restore/quality; пустой зарезервированный файл не
является измерением. Aggregate `passed` относится только к участникам с заданными criteria;
участники `not_requested` не становятся научно принятыми из-за общего badge.

Общий C++ `run_batch` вызывается непосредственно из фонового worker, без Python/CLI subprocess.
Общие close guard, frozen endpoint и запрет параллельного запуска действуют и для серии.
При ошибке подготовки rows/path/badge очищаются; готовый batch.json при таком отказе не обещается.
Этот режим исполняет сохранённый план одной записи. Для нового состава используйте режим ниже;
multi-recording supervisor, переносимый bundle, durable resume и сравнение произвольных отчётов
остаются отдельными задачами.


### Визуальное составление серии

1. В **Исследования → План → Источник плана** выберите **Составить серию**.
2. Нажмите **Добавить сценарий…** и выберите локальный scenario JSON. Повторите для следующих
   участников; один файл допускается несколько раз. Лимит — восемь сценариев.
3. Кнопками **↑ / ↓** установите порядок; **Удалить** убирает участника. ID `case-N` создаётся
   автоматически и не меняется при перестановке. Удалённый ID может использоваться новой строкой;
   уникальность обеспечивается внутри текущей серии, не между разными запусками.
4. Укажите новый каталог с существующим родителем и нажмите **Начать исследование**.
   Пустую серию запустить нельзя. При запуске состав копируется и редактор блокируется;
   форма одиночного сценария/её reference к этой серии не применяются.
5. Все сценарии должны задавать `reset_replay=true` и относиться к одной подключённой записи.
   `FileExperiment` разрешает reference относительно исходного canonical scenario path.
   Проверка всех сценариев, эталонов, IDs и общих budgets выполняется в worker до output/сети.
6. После preflight до подключения сохраняется `OUTPUT/inputs/plan.json` с абсолютными путями
   к выбранным сценариям. Общая сводка `batch.json` содержит `plan_snapshot: "inputs/plan.json"`.
   Progress, cancel и результаты используют тот же контракт, что запуск сохранённого плана.

Сформированный файл можно выбрать в режиме **Запустить batch-план** или передать CLI:

```sh
build/svctl --unix /tmp/sv-prototype --timeout-ms 10000 research-batch \
  artifacts/my-series/inputs/plan.json artifacts/my-series-repeat
```

Это ссылки на локальные исходники: сохраните scenario files, reference manifests и их данные.
План не копирует dataset, не закрепляет содержимое файлов на будущие запуски и не переключает
сервер на другую запись. Каждый прогон заново фиксирует/хэширует входы. Перенос между машинами
пока требует подготовки тех же файлов/путей; bundle export остаётся открытым.

C++ overload `run_batch(document, scenario_base_directory, output_directory, options, cancel,
progress)` принимает документ из памяти. Он сериализуется как compact JSON + newline;
`plan_sha256` совпадает с точными bytes snapshot. Файловый и memory входы используют одну
проверку и один исполнитель. Для прямого C++ вызова относительные пути разрешаются от явного
base; его snapshot нельзя механически повторить из другого каталога без исходной base или
перевода ссылок в абсолютные. GUI всегда записывает абсолютные пути, поэтому его snapshot
пригоден для указанного CLI rerun. Файловый overload сохраняет прежний raw-byte hash и не
добавляет snapshot. Схема summary остаётся1, `plan_snapshot` — optional extension.

Входы проверяются до создания outputs; ошибка резервирования/записи после preflight может
оставить частичный каталог, но сетевые мутации ещё не начинались. Запись snapshot не является
fsync/durable journal. Импорт готового batch в редактируемый список описан ниже. Сохранение
неисполненного черновика отдельной командой реализовано ниже; редактирование параметров
каждого scenario в этой панели пока не реализовано. Отдельный QML компонент хранит только состав; C++ builder проверяет типы/URL,
общий runner — содержимое и budgets. Трасса: рисунок RR.10 в [[architecture/RESEARCH_RUNTIME]].


### Импорт плана в редактор серии

1. Откройте **Исследования → План → Составить серию → Импортировать план…**.
2. Выберите обычный локальный batch JSON схемы1 размером1…65536bytes, например сохранённый
   `OUTPUT/inputs/plan.json`. Импорт доступен и без подключения к серверу.
3. Успешный импорт **заменяет текущий состав целиком**. При ошибке чтения/JSON/схемы/ID либо
   отмене диалога прежний состав сохраняется; текст ошибки находится под кнопкой импорта.
   Дубликаты ID, reserved ID `batch`, неизвестные поля и более восьми участников отклоняются.
4. ID и порядок исходного плана сохраняются. Относительные scenario paths разрешаются от
   каталога **выбранного batch file**, как в CLI. Для symlink самого batch базой остаётся
   каталог выбранной ссылки; это отличается от canonical base отдельного FileExperiment.
5. Переставьте/удалите участников или добавьте новые сценарии. Автоматический `case-N` выбирает
   свободный ID с учётом импортированного списка. Исходный batch file не перезаписывается.
6. Отдельно выберите новый output и нажмите **Начать исследование**. Входы/эталоны и budgets
   проверяются заново общим C++ runner; результатом будет новый `inputs/plan.json` и reports.

Импорт проверяет **структуру**, не существование/содержимое scenario files или references:
отсутствующий сценарий можно убрать из списка до запуска. Успешный импорт не означает
готовность набора данных или прохождение quality criteria. Планы и references находятся на
машине `sv-simulator`; подключённый сервер должен уже использовать совместимую replay-запись.
При активном исследовании импорт блокируется, текущие report/quality state не изменяются
из-за ошибки импорта. Новых серверных команд нет.

Структурный parser `parse_batch_plan` общий для импорта и обоих run_batch overload.
`read_batch_plan` сохраняет точные bytes для CLI digest, читает максимум65537bytes для проверки
верхней границы и принимает обычный файл, включая symlink на него. FIFO/директории/специальные
файлы отклоняются; O_NONBLOCK при open предотвращает ожидание writer у FIFO. GUI выполняет
этот небольшой синхронный импорт; datasets/references загружаются только в execution worker.
Ограничение размера чтения не является deadline для дискового IO.

При преобразовании file URL абсолютный путь сохраняется без lexical удаления `..`:
`link/../scenario.json` при symlink `link` может ссылаться на иной файл, чем нормализованный
`scenario.json`. Это поведение проверено регрессионным тестом на Linux/Qt6; исходный сценарий
и его reference затем разрешаются обычным FileExperiment. Импорт не создаёт копию datasets,
не переключает серверную запись. Сохранение неисполненного draft — отдельное действие ниже.
Трасса — рисунок RR.11 в [[architecture/RESEARCH_RUNTIME]].


### Сохранение черновика без исполнения

1. В **Исследования → План → Составить серию** добавьте сценарии или импортируйте план,
   затем задайте нужный состав и порядок. Подключение к серверу не требуется.
2. Нажмите **Сохранить черновик как…**, выберите существующий родительский каталог и **новое**
   имя JSON файла. Пустую серию сохранить нельзя. Существующий файл не заменяется, включая
   hard links и symlinks; выберите новое имя для следующей версии.
3. Сообщение под кнопкой показывает результат записи. Отмена диалога ничего не сохраняет.
   Ошибка не меняет состав, предыдущий файл и результаты последнего исследования.
4. После изменения состава появляется сообщение, что он отличается от сохранённого.
   Возврат к прежнему составу/порядку возвращает отметку совпадения с ранее сохранённым черновиком.
   Это сравнение состава в UI, не проверка существования или актуальности файла на диске.
5. Сохранённый файл можно импортировать в редактор или выбрать в **Запустить batch-план**,
   либо передать CLI:

```sh
build/svctl --unix /tmp/sv-prototype --timeout-ms 10000 research-batch \
  /path/to/drafts/series.json artifacts/series-run-01
```

Файл содержит обычный schema1 plan с ID, порядком и абсолютными scenario paths, без специальных
GUI полей. Его можно переместить в другой каталог: исходные scenario/reference/data должны
оставаться доступны по тем же путям. Импортированные относительные ссылки сначала разрешаются
от исходного batch directory; file URL и symlink/.. сохраняют filesystem meaning.

Сохранение проверяет структуру общим `parse_batch_plan` до создания файла, но не читает
scenarios/references, не проверяет reset_replay/совместимость записи/общий runtime budget
и не запускает исследование. Отсутствующие сценарии допустимы для сохранения черновика.
Полный preflight обязателен при исполнении. `ResearchController.saveBatch` возвращает локальные
success/path/sha256/message; прежние reportPath/quality/exitCode не меняются. Пока worker активен,
сохранение отклоняется; UI также блокирует редактор.

C++ `write_batch_plan(document, file)` проверяет сериализованный документ, вычисляет SHA256
compact JSON + LF и использует общий ReportOutput/O_EXCL. Digest возвращается отдельно,
в schema1 JSON дополнительных полей не появляется. Путь сохраняется без lexical сокращения
symlink/..; проверены identity источника и назначения. Родительские каталоги автоматически
не создаются. Ошибка IO после reservation может оставить пустой/частичный новый файл;
повтор требует нового имени. Это не fsync/durable journal и не dataset bundle.

Qt6 SaveFile dialog использует DontConfirmOverwrite, поскольку backend всё равно принимает
только новый файл; значение флага соответствует
[официальному контракту Qt FileDialog](https://doc.qt.io/qt-6.5/qml-qtquick-dialogs-filedialog.html).
Защита записи обеспечивается C++, независимо от поведения диалога. Qt5 wrapper подготовлен
по существующему шаблону export dialog; отдельная Qt5/Aurora приёмка остаётся открытой.
Трасса: рисунок RR.12 в [[architecture/RESEARCH_RUNTIME]].


Сохранённые individual reports можно сопоставить без сервера во вкладке
**Исследование → Сравнение**: [[engineering/RESEARCH_REPORTS]]. Для batch выбирайте
конкретные `ID.json`, а не индекс `batch.json`.

## Каталог возможностей в форме исследования

В режиме **Настроить через форму** варианты fusion определяются каталогом текущей
сессии `configurationEditor.catalog.fusion`, уже полученным через ConfigService.
Нового запроса или дополнительного соединения ради формы нет. До загрузки каталога
форму можно редактировать, но запуск недоступен. При disconnect/reset каталог очищается
существующим ConfigurationEditor, и запуск снова блокируется.

C++ адаптер `research_capabilities` вычисляет пересечение известных клиенту и объявленных
сервером значений. Поддержаны fusion catalog versions1–5 с diagnostic `color`.
Неизвестные методы/границы/решатели не добавляются автоматически; неизвестная версия,
неверные типы/диапазоны и дубли enum отклоняют каталог. UI показывает известные методы
и помечает недоступные. Для graph-cut нужны явно объявленные seam solvers; для multiband —
известные границы и непустое пересечение уровней с клиентским диапазоном1…8. Отсутствие
этих сведений отключает соответствующее семейство, сохраняя остальные методы.

Граница **Сравнить обе** доступна только при объявленных `zero` и `normalized`.
ComboBox выбирает boundary/solver по имени, а не позиции в списке сервера. При обновлении
каталога прежнее имя сохраняется; отсутствующее значение показано как недоступное.
Выбранный неподдерживаемый метод остаётся отмеченным и его можно снять явно. Таким
образом, обновление каталога не превращает ранее задуманный опыт в другой метод.
Число уровней также сохраняется; разрешённый сервером диапазон показан над формой.
За пределами диапазона запуск блокируется, пока пользователь явно не исправит число.
Граница/уровни не применяются к непирамидальным методам, solver — к методам без graph-cut.

`draftCapabilities` и `draftCapabilityError` дают UI доступные значения и причину отказа.
Кнопка формы вызывает `startCatalogDraft`: C++ повторно строит обычный scenario и проверяет
его по переданному snapshot каталога **до** запуска worker, output reservation и сетевых
операций. Затем используется прежний `startDraftWithReference`/FileExperiment/runner.
Сохранённые scenarios/batch не фильтруются по этому UI каталогу: ими по-прежнему управляет
общий runner и авторитетная серверная проверка. Прежние C++ методы запуска формы остаются
application API без обязательного GUI snapshot; они также не обходят серверную валидацию.

Каталог описывает объявленные возможности, а не резервирует revision, backend, память или
пиксельный бюджет. Между подготовкой формы и подключением runner сервер может измениться.
Фактический `fusion_catalog` вновь запрашивается runner и сохраняется в report; ошибки
исполнения проходят обычный restore/report workflow. Дополнительные capability guards
протокола, carrier/parameter matrices, остальные численные поля fusion и редактор quality
criteria остаются отдельными пунктами [[planning/ROADMAP]].

Проверки и ограничения: [[validation/RESEARCH_RUNTIME]]; процесс:
[[architecture/RESEARCH_RUNTIME#Выбор профиля исследования по каталогу сервера]].

## Матрица параметров fusion в форме

В **Исследование → План → Настроить через форму** блок **Матрица параметров** добавляет:

- диапазон уровней пирамиды: от/до/шаг, целые1…8;
- сравнение `binary_pairs` и `alpha_expansion`;
- их сочетание с выбранными methods и прежним boundary `zero`/`normalized`/обе.

При включении диапазона одиночное поле levels временно отключается; при сравнении solver
отключается одиночный solver. Прежние значения сохраняются для возврата к одиночному режиму.
Верхняя граница включается только если достижима шагом: от2 до5 с шагом2 даёт2 и4,
не добавляя5 автоматически. У каждого применимого метода проверяются все выбранные значения
по текущему каталогу. Сужение каталога не сужает диапазон и не отменяет solver comparison
молча — нужно явно исправить выбор. Checked solver comparison можно снять и после потери
одного solver из каталога.

Диапазон используется только у multiband, solver axis — только у graph-cut. Например,
`edge_feather + graph_cut_seam + multi_band + graph_cut_multi_band`, levels2/4,
две boundaries и два solver дают **1+2+4+8=15** variants. Полный Cartesian product всех
полей для всех методов дал бы повторные варианты с неиспользуемыми параметрами.
При временном снятии всех методов нужного семейства его ось исключается из scenario,
а выбранные UI значения сохраняются для последующего явного возврата.

`research_matrix_draft` — C++ form adapter; он для каждого метода вызывает общий
`expand_variant_matrix` с применимыми axes. Порядок methods сохраняется, порядок axes
совпадает с детерминированным common expander. Обычный scenario snapshot содержит полный
готовый список `variants`, а не новый формат исполнения. Такой файл можно повторить
через прежний `svctl research`; UI range/checkbox state отдельно не сериализуется.
Критерии/reference продолжают фиксироваться прежним общим FileExperiment.

Сводка quantities также поступает из C++ `draftSummary`: variants, frames, blocks, trials.
При недопустимом диапазоне/превышении лимита вместо ложного нулевого числа показана ошибка.
Preview не читает references и не открывает соединения, не подтверждает достаточность памяти,
пиксельного бюджета или геометрии. Прежние пределы32 variants/10000 trials действуют на весь
профиль; ошибка блокирует запуск до worker/output/network. Окончательная проверка принадлежит
серверу.

Внутренние дополнительные поля form API: `pyramid_levels_range={from,to,step}` и
`seam_solvers=[...]`; второе принимает один или два различных известных solver. Обычные
scenario schema1 используют прежний список variants, новые form keys туда переносить не надо.
Диаграмма: [[architecture/RESEARCH_RUNTIME#Матрица параметров fusion в форме исследования]].

Применимые числовые оси добавлены ниже. Матрицы других параметров, редактируемый импорт формы
и bundles/multi-recording остаются отдельными задачами.

Карточки результата показывают индекс variant и применимые levels/solver, чтобы матрица
не давала одинаково подписанные строки. Текст переносится, высота подстраивается. Подпись
описывает scenario; actual settings и source identities находятся в sample metadata и
проверяются live integration test. Время одного paused sample не задаёт рейтинг алгоритмов.


## Набор носителей в форме

Во вкладке исследования появились отдельный набор носителей и переключатель
«Сравнивать набор носителей × варианты сшивки». Ввод JSON не нужен:

1. В конфигураторе задайте тип, размеры и сетку носителя. Выполните серверные
   validate/apply, затем обновите active. Неприменённый черновик не участвует.
2. В исследовании нажмите «Добавить текущий active». Добавляется независимая копия
   полного объекта surface, включая support/occlusion и параметры сетки.
3. Повторите для других носителей или размеров. Можно удалить отдельный профиль.
   Полностью одинаковый объект повторно добавить нельзя; разные размеры одного
   типа допустимы. Набор живёт в текущем окне и не меняется при смене active.
4. Включите сравнение набора, выберите методы/оси fusion. C++ preview показывает
   полный объём эксперимента. Например,5 носителей ×4 fusion variants =20 variants.
5. Запустите в новую выходную папку. `scenario.json` фиксирует полные объекты
   `variants[].surface`; его можно повторить через `svctl research`. Отдельного
   GUI-only формата исполнения нет. До запуска набор автоматически на диск не сохраняется.

Выключенный набор сохраняется в форме, но не попадает в scenario: runner использует
исходный носитель сервера. Включённый пустой набор блокирует запуск. Лимиты32 variants
и10000 trials общие, а не на каждый носитель. Порядок: профили в порядке добавления,
внутри каждого — детерминированный список fusion variants. Случайный порядок реальных
trial задаётся прежним seed и отражается индексом variant в samples.

До worker/output проверяются полные дубликаты, наличие required geometry fields,
известный тип и доступность типа в surface catalog текущей сессии. Семантика размеров,
совместимость с vehicle/view, optional-поля и ресурсная допустимость окончательно
проверяются сервером при применении. Старый active snapshot не является разрешением
для новой машины или изменённой конфигурации. Сужение catalog не удаляет профили молча.

Внутреннее поле формы `surface_profiles=[{type,...},...]` разворачивается C++ adapter
в обычные schema1 variants. В карточке показаны индекс и тип носителя; точные размеры,
optional-параметры и подтверждённая actual geometry находятся в scenario/sample metadata.
Runner проверяет actual surface и восстанавливает исходную поверхность, fusion и pause.
Курсор replay этим восстановлением не охватывается. Диаграмма:
[[architecture/RESEARCH_RUNTIME#Матрица носителей: снимки active, а не черновиков]].

## Числовые списки параметров fusion

В «Матрица параметров» раскройте «Показать списки числовых параметров».
У каждого параметра включите список, задайте число SpinBox и нажмите «Добавить»;
отдельные значения удаляются кнопкой. Ввод JSON или строк с разделителями не нужен.
Допускается1..8 различных конечных значений на ось. Включённый пустой список блокирует
запуск. Сворачивание группы скрывает controls, но не отключает выбранные оси.

| Ось | Допустимые значения | Применимые color methods |
|---|---|---|
| Ширина смешивания, px | (0,4096] | edge_feather, angular_feather, multi_band |
| Степень углового веса | (0,32] | angular_feather |
| Smoothness graph-cut | [0,100] | graph_cut_seam, graph_cut_multi_band |

UI вводит числа с точностью0.001; C++ принимает конечные числа в указанных пределах.
Явный список исключает накопление ошибки десятичного шага. Порядок значений сохраняется;
общий expander сортирует имена axes. Неприменимые оси не увеличивают число вариантов,
а выбранный список сохраняется при смене методов. Это не обещание различающихся кадров:
на конкретном входе две применимые настройки также могут дать одинаковый результат.

У hard_best_angle положительная степень сохраняет математический порядок угловых весов,
поэтому перебор этой степени в форме не создаётся. Численные underflow-эффекты не являются
предметом этой оси. У graph-cut edge weight слоя не используется как вес выбора шва;
graph_cut_multi_band строит blend weights из найденных cut labels, поэтому ширина также
не добавляется этому методу. Основание — текущие `src/render/surface.frag` и
`src/fusion/fusion.cpp`; при изменении алгоритмов таблицу и тесты нужно обновлять.

Без явных списков действуют defaults Scenario/FusionSettings: edge_width24,
angle_power2, smoothness0.1; значения active сервера не наследуются. Каталожная проверка
охватывает все три фактически отправляемых числа, включая defaults, для каждого variant.
Это позволяет отвергнуть суженный/неполный catalog до worker/output. Сужение catalog не
удаляет сохранённые значения. Все оси, carrier profiles и блоки делят лимиты32 variants и
10000 trials. Ошибка показывается в preview и блокирует старт.

Внутренние поля формы: `edge_width_values`, `angle_power_values`, `smoothness_values`.
Они разворачиваются C++ adapter в обычные `variants[].edge_width_px/angle_power/smoothness_weight`.
Карточка результата показывает числовые поля сохранённого scenario, включая нормализованные
defaults отчёта; actual значения находятся в metadata.
Сценарий и отчёт повторно используются через compiled runner без Python.

## Переносимый набор сценария

Реализован compiled C++ формат **scenario_bundle_v1** для одного сценария и его
client-side quality reference. Он переносит необходимые RGB/mask PPM и переписывает
ссылки в относительные. **Replay, конфигурация/калибровка сервера и build не включены**:
на целевой машине нужно отдельно подготовить тот же recording и совместимый sv-server.
Это первый срез bundle workflow, а не архив всего стенда.

```text
experiment-bundle/
  bundle.json
  scenario.json
  reference.json                  # только при quality_reference
  assets/
    frame-0-rgb.ppm
    frame-0-mask.ppm
    ...
```

`bundle.json` содержит schema_version1, kind=scenario_bundle_v1,
scope=client_scenario_and_reference_only, source_scenario_sha256, список
files[{path,bytes,sha256}] и reference_description либо null. Source digest относится к
исходным bytes сценария до переписывания пути; descriptor scenario.json — к уже
упакованным bytes. Reference description фиксирует нормализованные guards/view/criteria,
decoded RGB/mask hashes и hash переписанного manifest. Оригинальное форматирование
reference manifest не сохраняется; исходные PPM bytes сохраняются без перекодирования.

### Команды

Экспорт и verify не создают подключения; endpoint flags для них не используются:

```bash
./build/svctl research-bundle-export configs/research/my-scenario.json artifacts/my-bundle
./build/svctl research-bundle-verify artifacts/my-bundle
```

Родитель выходной папки должен существовать, сама папка должна быть новой. Папку можно
скопировать целиком на другую машину или переместить. После проверки запустите:

```bash
./build/svctl --unix /tmp/sv-prototype research-bundle-run artifacts/my-bundle artifacts/bundle-report.json
./build/svctl --tcp 192.168.1.20 53101 53102 research-bundle-run artifacts/my-bundle artifacts/remote-bundle-report.json
```

Порты — пример, используйте настроенные серверные control/data endpoints. Сервер уже
должен работать с нужной replay-записью. К нему применяются прежние lease/catalog/source/
quality guards. Программа возвращает обычные research exit codes:0 — завершено,
4 — техническая/неполная попытка,5 — завершённое отклонение качества; ошибки bundle
preflight дают3 до резервирования report и соединения. Неверные аргументы дают2.

`research-bundle-run` самостоятельно заново проверяет bundle; отдельный verify — удобная
offline-проверка, а не разрешение обходить проверку при последующем запуске.
Использование обычного `research bundle/scenario.json ...` технически возможно,
но не проверяет bundle inventory и не записывает input_bundle provenance; для bundle
workflow используйте специальную команду.

### Проверка и фиксация входов

`ScenarioBundle` сначала читает ограниченный manifest, затем только перечисленные
файлы фиксированной структуры. Absolute paths, `..`, неизвестные имена и дубликаты
в inventory отвергаются; root/asset directory и file leaves открываются без следования
финальным symlink. FIFO/устройства не принимаются. Посторонние **физические** файлы,
не перечисленные в manifest, не читаются; лишние **inventory entries** отвергаются.
Reference может ссылаться только на перечисленные assets. Проверяются actual sizes и
SHA256; после этого verified bytes копируются в private staging directory (mode0700).
FileExperiment фиксирует decoded reference и сверяет его description с manifest.

После конструктора все входы уже зафиксированы: удаление/изменение исходного bundle
не меняет execute. Открытие report и подключение происходят позже. `execute` допускает
одну попытку; второй вызов не создаёт другой output. Staging удаляется при уничтожении
объекта; путь scenario_input_base_directory в report является временным и не служит
путём для последующего ручного воспроизведения. Сохраняйте исходный bundle.

Report получает scenario_input_kind=verified_bundle_snapshot_v1 и объект input_bundle
с policy, manifest_sha256, source_scenario_sha256 и scope. Это идентичность проверенного
снимка, не доказательство авторства, неизменности server recording или независимости
reference. Изменение данных и согласованное редактирование unsigned manifest создают
другой допустимый набор; доверенная подпись этим форматом не реализована.

### Пределы и неготовые части

- Bundle manifest/scenario/reference JSON — до1MiB каждый; reference до256 frames.
- До514 перечисленных файлов, не более16MiB на PPM и64MiB суммарных member bytes.
  Manifest имеет отдельный предел1MiB. Это не ограничение RSS; decoded reference
  дополнительно проходит прежний128MiB pixel budget.
- Экспорт сначала валидирует copied inputs в private staging и только потом создаёт
  новую целевую папку. Файлы создаются исключительно; manifest записывается последним.
  При I/O error/cancel может остаться частичная новая папка. Existing output не очищается
  и не заменяется. Atomic publication/fsync/durable resume не реализованы.
- Cancel проверяется между chunks/файлами и до execute; он не прерывает уже выполняющийся
  syscall или parser/decoder. Входы должны быть обычными локальными файлами.
- Экспорт сохранённого сценария, offline-проверка и запуск набора доступны в svctl и
  sv-simulator. Экспорт текущей несохранённой формы, batch/multi-recording bundles,
  server config/dataset/build registry, архивный контейнер и deduplication остаются открытыми.

API: export_scenario_bundle(path,new_directory,cancel), ScenarioBundle(path,cancel),
summary(), execute(new_report,client_options,cancel,progress). Они используют тот же
FileExperiment/ExperimentRunner, не запускают Python и не добавляют wire commands.
Диаграмма: [[architecture/RESEARCH_RUNTIME#Переносимый набор сценария и эталона]].


### Переносимый набор в sv-simulator

1. Откройте **Исследования → План → Источник плана → Переносимый набор**.
2. Для готового набора нажмите **Выбрать папку…** и выберите каталог с bundle.json.
   **Проверить без сервера** проверяет файлы в worker и показывает квитанцию: путь,
   число members и SHA256 manifest. Подключение не требуется.
3. Для экспорта раскройте **Экспортировать сохранённый сценарий**. Выберите JSON-файл
   сценария и родительскую папку; введите только имя новой папки, затем нажмите
   **Экспортировать без сервера**. Экспортируется выбранный файл, а не форма другой
   вкладки. Relative reference разрешается от исходной папки сценария. Имя не должно
   содержать разделители, `.`/`..` или пробелы по краям. Existing destination не заменяется.
4. После экспорта выберите созданную папку для запуска. Подготовьте соответствующую
   replay-запись на сервере и подключитесь через основной экран. Укажите новый каталог
   результата с существующим родителем и нажмите **Начать исследование**.
5. Запуск заново читает и проверяет bundle, фиксирует его входы, затем создаёт каталог
   с report.json и использует обычный research protocol. Прогресс/отмена/restore,
   таблица измерений, quality status и сравнение отчётов работают как для обычного сценария.

Квитанция показывает предыдущее чтение; она не заменяет проверку при запуске и не
означает scientific acceptance. При новой операции квитанция и прежний результат
сбрасываются. Ошибка проверки не создаёт каталог отчёта. Экспорт/verify/run и обычные
исследования взаимоисключающие, используют один worker и общий close/cancel guard.
Отмена файловой операции доступна кнопкой **Отменить текущую операцию** на вкладке
План; после начала серверного прогона — на вкладке Выполнение. При завершении
файловой операции нет server restore, потому что подключения не было.

Чтение, hashing, copying и reference decode выполняются вне GUI-потока. Входы ограничены
пределами общего сервиса выше; переносится client-side reference, не server recording.
Qt6/Linux проверен автоматически; диалоги Qt5 подготовлены, но Aurora/Qt5 требуют
отдельной проверки. Последовательность: [[architecture/RESEARCH_RUNTIME#Переносимый набор в GUI]].

## Переносимая серия одной записи

`BatchBundle` переносит упорядоченный batch-план из1–8 сценариев вместе с их client-side
PPM references. Все сценарии выполняются последовательно на **одной уже подготовленной
серверной записи**. Серверные recording/config/build не входят, запись между сценариями
не переключается. Это отдельный формат `batch_bundle_v1`; GUI режима «Переносимый
набор» пока принимает только одиночный `scenario_bundle_v1`.

```bash
./build/svctl research-batch-bundle-export artifacts/plan.json artifacts/portable-series
./build/svctl research-batch-bundle-verify artifacts/portable-series
./build/svctl --unix /tmp/sv-prototype research-batch-bundle-run artifacts/portable-series artifacts/series-results
```

Подставьте существующий план и новые каталоги с существующими родителями. Export и
verify не подключаются к серверу. Для TCP используется обычный `--tcp HOST CONTROL_PORT
DATA_PORT`. Run возвращает0 при завершении без провала критериев,5 при завершённом
провале заданных критериев,4 при technical failure/incomplete и3 при ошибке подготовки;
аргументы CLI —2. Quality rejection не останавливает следующие сценарии; technical
failure или cancel останавливает. Ошибка restore отражается отдельно в summary.

### Manifest, фиксация и output

```text
portable-series/
  bundle.json              # batch_bundle_v1
  run-0/
    bundle.json            # scenario_bundle_v1
    scenario.json
    reference.json         # если задан
    assets/frame-0-rgb.ppm
    assets/frame-0-mask.ppm
  run-1/
    ...
```

Top manifest содержит ровно schema_version=1, kind=batch_bundle_v1,
scope=client_scenarios_and_references_only, source_plan_sha256 и runs. Каждая строка
runs содержит id, directory и manifest_sha256. Directory фиксирован по позиции:
run-0..run-7. ID проверяются правилами обычного batch: уникальные безопасные имена,
не `batch`. Manifest hash связывает точные bytes child manifest, а тот связывает свои
scenario/reference/assets. ID и порядок сохраняются, source_plan_sha256 относится к
исходным bytes plan, а plan_sha256 отчёта — к построенному внутреннему плану.

Конструктор читает top manifest с пределом64KiB, копирует только фиксированные child
paths в private staging, проверяет child hashes, closure и decoded reference через
ScenarioBundle и проверяет суммарные бюджеты до output/network. Root, run-N, assets и
file leaves открываются no-follow; FIFO/devices отвергаются. После конструктора удаление
или изменение исходного набора не влияет на execute. Один объект допускает одну
попытку execute; pre-cancel проверяется до output. Общий executor резервирует batch.json
и все member reports до первого подключения, затем использует прежний runner.

Результат — новый каталог с batch.json, `<id>.json` и RGBA captures. Summary получает
input_bundle с top identity и ordered child receipts; individual reports сохраняют
свои child identities и scenario_input_kind=verified_bundle_snapshot_v1. Для
невыполненных сценариев зарезервированные reports могут оставаться пустыми: статус
смотрите в summary.runs. Внутренние run-N paths относительны **bundle**, а не output;
inputs/plan.json для такого запуска не создаётся. Для повторения сохраняйте bundle и
используйте research-batch-bundle-run, не извлекайте внутренний план как готовый launcher.
Private staging paths в individual reports временные.

### Бюджеты и ограничения

- До8 child bundles, до10000 trials суммарно; каждый сценарий обязан reset_replay=true.
- До64MiB суммарно на child manifests и перечисленные child files; top manifest имеет
  отдельный предел64KiB. Single-child limits остаются прежними: до514 members,
  JSON до1MiB, PPM до16MiB, до256 reference frames.
- До128MiB суммарных decoded references. Это предел принимаемых данных, не гарантия RSS
  или пикового staging disk usage: временные копии, raw/decoded buffers и preflight
  последнего child требуют дополнительного пространства.
- Экспорт сначала проверяет всю серию в private staging, потом создаёт новый destination,
  копирует child bundles и пишет top manifest последним. Existing output не заменяется.
  При I/O error/cancel может остаться новая неполная папка. Atomic publication/fsync,
  resume/checkpoints, подпись, deduplication и архивный контейнер отсутствуют.
- Hashes подтверждают согласованность с unsigned manifest, не независимость truth,
  авторство, неизменность server dataset или scientific acceptance.
- Batch GUI, экспорт несохранённой формы, multi-recording supervisor и server registry
  остаются в TODO. Продуктовый сервис и CLI — C++; Python используется только как harness.

API: export_batch_bundle(plan,new_directory,cancel), BatchBundle(path,cancel), summary(),
execute(new_output,options,cancel,progress(member,done,total)). Схема взаимодействия:
[[architecture/RESEARCH_RUNTIME#Переносимая серия одной записи]].
