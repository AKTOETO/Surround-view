# Требования к системе Surround View

## Назначение и статус

Редакция от 19.09.2026 по [аудиту](Аудит_и_план_3D_Surround_View.md). Это спецификация планируемой системы; наличие документа не подтверждает реализацию или достижение метрик. Требование выполнено, когда существует реализованное поведение и подходящее свидетельство: тест, инспекция или измерительный протокол.

Цель — разработать интерактивный круговой обзор по изображениям четырёх fisheye-камер и экспериментально определить влияние формы и дискретизации проекционной поверхности на точность, время GPU-рендеринга и отклик виртуального ракурса. Bowl, GPU и изменяемый ракурс уже представлены у TI [1]; собственный вклад проверяется сравнением способов дискретизации, а не объявляется заранее.

## Область и приоритеты

**MUST** — обязательный защищаемый результат. **SHOULD** — желательное расширение; отсутствие объясняется в отчёте. **COULD** — дополнительная возможность после завершения основного исследования. Приоритет требования о метрике означает обязательность измерения; численный порог остаётся предварительным до фиксации профиля по [VALIDATION.md](VALIDATION.md).

| Уровень | Состав |
|---|---|
| Исследовательское ядро | `sv-core`: модель `opencv_fisheye`, аналитическая bowl, равномерная и исследуемая сетка, независимый CPU-эталон, GPU-проекция, маски, blending, виртуальная камера; `sv-bench` для опытов |
| Минимальный демонстрационный стенд | Один Linux-узел; отдельный `sv-server`; `sv-ui` на Qt 5.15, Qt Quick (QML) [2]; лёгкий `sv-simulator` как producer; локальный replay без simulator; trace |
| Желательные интеграции | Реальная калиброванная запись, live-адаптер, передача GPU-буфера при измеренном узком месте; CAN/сенсоры только для конкретного сценария |
| Дополнительные возможности | Полный интерактивный 3D-мир, динамика автомобиля, pan, hot-swap, горячая калибровка, другой графический API |

Обязательных физических камер ровно четыре: `front`, `right`, `rear`, `left`. Отсутствие одной — отказ, а не отдельная конфигурация системы с меньшим числом камер. Габариты, калибровка и поверхность меняются данными. Два физических компьютера и конкретное головное устройство не являются условиями минимального стенда.

## Термины и исследовательские задачи

Проекционная поверхность — условная 3D-геометрия для отображения изображений, а не восстановленная сцена. Физическая камера формирует вход; виртуальная камера задаёт выходной ракурс. Набор кадров содержит выбранные входы с их идентификаторами и временем. Возраст набора вычисляется по старейшему входу; skew — разброс времён входов в общей шкале. Программная сквозная задержка заканчивается событием передачи результата на представление в UI и не равна измерению появления пикселя на экране.

| Задача | Содержание |
|---|---|
| R1 | Анализ аналогов и уточнение гипотезы |
| R2 | Математическая модель, калибровка, независимый эталон и метрики |
| R3 | Базовый GPU-конвейер четырёх камер |
| R4 | Дискретизация с учётом ошибки проекции и сравнение с равномерной сеткой |
| R5 | Интерактивный стенд, replay и диагностика |
| R6 | Сравнительные эксперименты, воспроизводимость и выводы |

## Границы результата

Обязательны orbit, zoom и пресеты; допустимая область задана в конфигурации. Скрытые стороны препятствий не восстанавливаются, вертикальные объекты могут растягиваться и двоиться. Покрытие и фотометрические швы оцениваются отдельно. Полноценная реконструкция, SLAM, оценка глубины, собственные нейросети, аппаратная синхронизация и функциональная сертификация не входят в объём.

Чтение фиксированного набора MUST; live-recorder SHOULD. Независимый CPU-эталон MUST. Смена адаптера между запусками MUST, hot-swap COULD. Критерии приёмки метрик задаёт NFR; конфигурация и паспорт фиксируют применённые значения. Предлагаемые аудитом ID `RES-*` распределены по действующим требованиям, отдельный дублирующий набор не вводится.
